# 试点与推广：四个自用仓库的落地实测

这份文档回答一个很具体的问题：**这套流程在真实项目里到底跑成什么样？** 不是 demo、不是设想，是四个自用仓库的实测快照。

- **数据时点**：2026-10-15（数字取自各仓库 `docs/process/**` 与 git 工作树）
- **采集方式**：直接读 frontmatter / journal / 旁挂 meta，并用插件工具复跑一遍（下文的数字都可用 §7 的方法复算）
- **脱敏口径**：仓库一律用代称（甲/乙/丙/丁），只保留技术形态，**不含仓库名、厂商名与业务字段名**；时间线里的需求语义也做了泛化
- **一句话结论**：流程本身跑得通、也能拦住真问题；**时间几乎全花在「人什么时候来看 Gate」上**，而机器侧证据在存量仓库里还偏薄（原因见 §5）

## 1. 四个仓库各自走到哪一步

| 代称 | 技术形态 | 流程落点 | 走到哪一步 | 卡在哪 |
| --- | --- | --- | --- | --- |
| **甲** | 规则校验服务（Node + TypeScript，CLI + 测试） | 已跑真实包 | **1 个包 `done`（含 Gate4 收口）+ 1 个包 `frozen`** | 没有卡住；第二个包按「小步切片」交付，仍在切片中 |
| **乙** | 通知类命令行工具 | 已跑真实包 | 1 个包 `draft`，journal 9 条、跨度 1.7h、1 次人签 | 卡在**立项澄清**：Gate1 前的口径还没定死，没人催就停在那 |
| **丙** | UI 组件演示 | 只落骨架（`prd/` 仍只有模板） | 未立包 | 卡在**没拿真实需求试水** —— 骨架装上了，但一直没开第一个包 |
| **丁** | 平台类服务 | 只落骨架（`prd/` 仍只有模板） | 未立包 | 同上；且仓库本身活跃（有近期提交），说明不是项目停了，而是**流程没被带进日常** |

两个可数的观察：

- **落地 ≠ 用起来**：4 个仓库都装了骨架（`docs/process/**` + `scripts/process/**` 齐全），但只有 2 个真的立过包。
- **停点会「无限期等待」**：乙的包停在等 Gate1，而 Gate1 只有人能签 —— 没有人来，它就一直停着（这不是 bug，是设计的代价，见 §2）。

## 2. 一个包的全流程脱敏实录（甲的第一个包）

需求：给一批数据按既有规则打标签并按约定格式输出（语义已泛化）。走的是 `full` 档，四个 Gate 全过，其中 **Gate0/1/2/4 全部由人签**。

| 相对时刻 | 环节 | 谁 | 事实 |
| --- | --- | --- | --- |
| +0.00h | intake | 主控 | 登记需求（含人给的初始裁定） |
| **+1.24h** | **Gate0** | **人签** | 通过：两个待裁定问题当场定死（主键口径 / 记录方式） |
| +1.24h | env | 主控 | 环境初始化 + 基线提交（git） |
| +1.29h | pm 交件 | subagent:pm | PRD（AC-1~AC-12，输出格式逐字冻结）+ 契约 + **设计与说明**（R-01~R-06 逐条对齐）+ UAT 清单 |
| +1.30h | errata | 主控复核 | 核对件出勘误 ER-01：**追加结论列数 9→8**（产物实测与 PRD 不符） |
| **+15.62h** | **Gate1** | **人签** | 通过并冻结契约 —— **距 pm 交件 14.3 小时** |
| +15.83h | 策略裁定 | 人签 | 「先在有限需求里看产出，肯定会不断调整」⇒ 改为小步切片推进 |
| +15.87h | test 写红 | subagent:test | 新增 10 文件 / 56 用例（绿 21 / 红 35） |
| +15.92h | 口径收口 | subagent:pm | 处理写红波次提出的 8 条口径问题（勘误 / 锚定现状，**判据语义不变**） |
| +16.01h | test 复跑 | subagent:test | 151 用例 115 绿 / 36 红（存量 94 全绿） |
| **+16.04h** | **Gate2** | **人签** | 通过 —— **距 Gate1 仅 26 分钟** |
| +16.24h | dev 交付 | subagent:dev | S1 实现：9 文件 `3307+/18-` |
| +16.55h | UAT | subagent:uat | 黑盒 18 条 = 通过 14 / **不通过 4** / 存疑 1 |
| +16.93h | UAT 复验 | subagent:uat | 针对不通过与存疑项定向复验 |
| +17.88h | **Gate4** | **人签** | 签署收口（人原话：「我只看输出的最终表格」）⇒ 切片完成、`status: done` |

**Gate 间隔实测耗时（这是整份文档里最有用的一组数）**

| 段落 | 耗时 | 性质 |
| --- | --- | --- |
| pm 出 PRD + 契约 + 设计与说明 | **约 4 分钟** | 机器侧 |
| test 写红（56 用例） | **约 5 分钟** | 机器侧 |
| dev 交付一个切片 | **约 11 分钟** | 机器侧 |
| UAT 黑盒一轮 18 条 | **约 1 分钟** | 机器侧 |
| 交件 → **Gate1 人签** | **14.3 小时** | **人侧（占全链路 80%）** |
| Gate1 → Gate2 人签 | **26 分钟** | 人侧（人在场时就很快） |

结论有三条，都反直觉：

1. **瓶颈不在 agent 干活，在「人什么时候来」**。机器侧每个环节都是分钟级；一次 14.3 小时的等待，就吃掉了全链路 17.9 小时里的 80%。
2. **人在场时 Gate 并不慢**。Gate2 只用了 26 分钟（因为写红/复跑/实现都已经并行做完了）。所以该压的是「人到的时机」，**不是去掉 Gate** —— 去掉 Gate 省下的是这 26 分钟，赔上的是整条链的质量归属。
3. **Gate 拦下的不是「agent 写错代码」，而是口径不清**。见 §4。

## 3. 规模量级

同一个包（甲的第一个包）的产物规模，可作为「一个中等需求」的参照：

| 项 | 量 |
| --- | --- |
| PRD | 458 行（含 AC 与验收口径） |
| 设计与说明 | 186 行（R-NN 逐条落地） |
| 契约 | 438 行（第二个包 459 行） |
| 测试 | 12 个测试文件 / 1563 行；一轮复跑 151 用例 |
| 该仓库入库文件 | 66 个；源码与脚本 41 个文件 / 10988 行 |
| journal | 31 条（FEAT-001）/ 19 条（FEAT-002） |

对「单人 + AI」这个形态，这个量级是合适的：**PRD 与契约加起来不到 900 行，但把口径冻到了可判定** —— 后面 dev / test / uat 三个角色冲突时，回看的就是这几百行。

## 4. 真实返工（都留了痕）

这些是实际发生的返工，注意它们的性质：

| 返工 | 性质 | 谁发现的 |
| --- | --- | --- |
| 勘误 ER-01：追加结论列数 9→8 | 产物实测与 PRD 不符 | 主控复核 pm 交付时 |
| 写红波次提出 8 条口径问题 | 判据字面不严 / 需锚定现状 | test 写红时 |
| 残余 4 条判据「字面冻死」 | 澄清 + **只收紧不放宽** | pm 收口 |
| 条款张力 Q-P / 措辞 Q-Q | 消歧与一致性修正（`prdVersion` 保持不变） | pm 收口 |
| UAT 18 条里 4 条不通过 + 1 条存疑 | 体验与预期不符 | uat 黑盒 |

**没有一条是「agent 把代码写错了」**，全部是**口径、字面、验收标准的对齐问题** —— 也就是「人该管的那部分」。这正是把角色边界放在提示词、把质量放在 Gate 人裁的理由：机器管可判定的那半，主观的与口径的留给人。

同时这也解释了为什么 **journal 必须逐条留痕**：上面每一条返工都能在 journal 里找到当时的判断依据（谁在什么环节、因为什么、改了什么）。事后再看，能分清「这是澄清」还是「这是放宽判据」——后者才是危险的。

## 5. 现存不一致清单（择要，含本次修复）

诚实列出这批仓库里还没对齐的地方：

1. **「从件遮蔽主件」——已在 0.5.0 修掉。** 从件（`<ID>-design.md` / `<ID>-ui-spec.md` / 清单件）的 frontmatter 也带 `id`，而扫描原本「先到先得」；`<ID>-` 在字典序上排在 `<ID>.` 前面，于是**设计件顶替了主件**：甲的两个包 `status=done` / `gate2=approved` 被报成 `status=confirmed` / `gate2=pending`。**这正是「用真实仓库验收」才能发现的 bug** —— 合成夹具里没有 `<ID>-design.md`，永远测不出来。修好后存量仓库**无需改动**，升级插件即恢复正确读数（见 CHANGELOG 0.5.0 / `docs/CONTRACT.md` 契约 1）。
2. **旁挂 meta 是旧格式**：只有 `lines` + `lastHash`，**没有 `chainHash`** ⇒ 这批仓库的 journal 目前**无法链式复算**（读取侧会如实报「⚠旧格式」，不会误报篡改）。要拿到链式指纹，需在仓库里跑一次 `process_init({ upgrade: true })`。
3. **`gate0` 只记在核对件里**，PRD 的 frontmatter 不记 —— 扫描没有问题，但人直接翻 PRD 时看不到 Gate0 是否签过。
4. **`bugs/` 是空的**：返工全靠 journal 的 `note` 记录 ⇒ 可追溯，但**不可机器统计**（想统计「这个包返工了几次」目前只能人读）。
5. **journal 旁有人工 `.bak` 备份**：流程产物目录里混进了手工备份文件（`*.journal.jsonl.bak`）。
6. **机器侧门禁证据偏薄**：这批仓库合计 9 条 `approve`、只有 2 条 `action:"run"`，且都**没有结构化退出码**（0.5.0 之前没有 `command`/`exitCode` 字段）⇒ 在这些仓库里，「跑过什么」目前**仍是自述**。这是升级到 0.5.0 之后最该补的一项。

## 6. 上马建议

按「最小代价跑通一次」排序：

1. **最小可用配置**：`PROJECT.md` 只需要 §1（产物清单）+ §2（命令槽）+ §3（产物属主表）。**§3 不填，落点门禁直接 `exit 1`** —— 这是新手第一个坎。
2. **先拿一个小而真的包试水**，别挑最大的需求。目标不是交付，是**走完一次 Gate0→Gate4**，把四个停点各体验一遍。
3. **升级要跑 `process_init({ upgrade: true, dryRun: true })`**：门禁脚本是**项目自带副本**，插件升级不会自动改它们；先 `dryRun` 看会动哪些文件，再落地。
4. **每次 Gate 后顺手看一眼**状态位与 journal 尾部（`process_status` / `gate_summary`），别攒着看 —— 攒着就会像乙那样停在等 Gate1，而没人知道。
5. **返工落 `bugs/`，别只写 journal note**（否则第 §5.4 条那种「统计不出来」会复现）。
6. **门禁命令要记 `action:"run"` + 真实 `exitCode`**（0.5.0 起）：这样 Gate 摘要能自动列出「exit 0 ✓ / exit 非零 🚨」，发布前扫一眼就知道缺口在哪。

## 7. 三个可数成功指标（都能机器核验）

| 指标 | 怎么算 | 这批仓库的实测 | 它不衡量什么 |
| --- | --- | --- | --- |
| **包收口率** | `status: done` 且 `gate4: approved` 的包 / 立过的包 | **1 / 3 ≈ 33%** | 不衡量「做得好不好」，只衡量流程有没有走到底 |
| **门禁证据密度** | journal 里 `action:"run"` 且带**非空 `exitCode`** 的条数 / `approve` 条数 | **0 / 9（0.5.0 之前无此字段）** | 不衡量测试写得多不多；低就说明「跑过什么」还是自述 |
| **人签等待占比** | Gate 从「交件」到「人签」的时长 / 全链路跨度 | **14.3h / 17.9h ≈ 80%** | **不衡量 agent 快不快** —— 它只告诉你瓶颈在人什么时候来 |

复算方法（都不需要装插件）：把包 frontmatter 与 journal 当纯文本读即可，例如

```bash
# 立过哪些包、各自的状态位（frontmatter 前几行）
for f in docs/process/prd/*.md; do
  case "$(basename "$f")" in _*|-*) continue;; esac
  printf '%s: ' "$(basename "$f")"; sed -n '2,8p' "$f" | tr '\n' ' '; echo
done

# 门禁证据密度：run 与 approve 各多少条（0.5.0 起 run 必带 exitCode）
jq -r '.action' docs/process/prd/*.journal.jsonl | sort | uniq -c

# 人签等待：把 approve 与它前面最后一次 write 的 at 相减即可
jq -r 'select(.action=="approve" or .action=="write") | "\(.at) \(.action)"' docs/process/prd/<ID>.journal.jsonl
```

契约字段与退出码口径见 [CONTRACT.md](./CONTRACT.md)；一条完整链路的核验脚本见 [ACCEPTANCE.md](./ACCEPTANCE.md)。

> **这份快照会过期**：它是 2026-10-15 的实测，仓库在继续推进。看数字时请连同日期一起看；采集方法写在上面，可自行复算。
