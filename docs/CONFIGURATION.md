# 配置你的仓库

插件本身不需要配置。要配置的是**你仓库里的流程**，而唯一的接口是 `docs/process/PROJECT.md`。

## 唯一接口：PROJECT.md

通用文档（`docs/process/README.md` 总纲、`orchestrator.md` 调度手册、`skills/**` 角色技能）只**引用** `PROJECT.md`，不硬编码任何具体项目的路径、命令与凭据。这带来两个承诺：

- **升级插件不会覆盖你填的 PROJECT.md**；
- **换项目只需重填 PROJECT.md**。

### 七个小节

| 节 | 内容 |
|---|---|
| §1 端与目录 | 本项目有哪些端（前端/后端/移动端…）、各自源码目录 |
| §2 命令槽 | 每类动作对应的命令（跑测试、起服务、打验收包…） |
| §3 产物属主表 | 哪些路径是可写落点、由哪个角色负责 |
| §4 项目配置 | 语言、包管理器、测试框架、自动化类型等取值 |
| §5 UAT 前置自检 | 真机验收前必须先满足的条件 |
| §6 环境与凭据 | 需要哪些环境变量与凭据 |
| §7 通知 | 可选 |

## 未填 = 未配置（占位符纪律）

模板里所有 `<...>` 都是**会被脚本忽略**的占位符。这是硬口径，不是建议——因为「假绿比红更危险」：

- **§3 可写路径**：含 `<` 或 `>` 的条目**一票不放行**。如果整列解析不到任何有效条目，落点门禁会**报错退出 1**，绝不静默放行。
- **§4 / §5 取值**：含 `<` 或 `>` 的取值视为未配置，**回落到「说明」列承诺的内置默认值**。因此模板里的示例值永远不会覆盖默认配置。
- **代码块内部不参与解析**：模板里的完整示例都放在围栏代码块里，照着抄不会污染机器读取。
- **变量路径别写 `<...>`**：用 `*` 通配（如 `scripts/*-*.{ts,sql}`），或者干脆不写进 §3、改在登记区**逐件登记**——后者更严格，推荐用于批次脚本。

## 门禁与流程脚本

`process_init` 会往你的仓库落一份脚本副本（零依赖，只用 `node:` 内置模块，可直接 `node` 跑）：

| 脚本 | 作用 |
|---|---|
| `journal-append.mjs` | 安全追加 journal（锁 + 指纹校验 + 原子替换） |
| `check-artifact-paths.mjs` | 校验产物是否落在 §3 允许的路径内 |
| `check-rules.mjs` | 校验流程规则（Gate、状态位、属主表） |
| `sync-prd-version.mjs` | 同步 PRD 版本号 |
| `project-config.mjs` | 上面几个脚本共用的 PROJECT.md 解析件 |

> **脚本是项目自带副本，不随插件升级自动更新。** 插件修了门禁逻辑之后，需要把这些脚本与 `docs/process/tools/README.md` 重新同步过去。

## 上下文是怎么进入会话的

AGENTS.md 那条老路（harness 读工作区指令文件）和插件不是替代关系，而是互补的三层：

| 层 | 载体 | 作用域 | 内容 |
|---|---|---|---|
| 框架级常驻 | 插件注册的 systemPrompt 段 | 该 profile 下**所有**工作区与 subagent | 6 行硬提醒：先调 `process_status`、Gate 必须人签、两段式、journal 纪律、角色由插件技能提供、真源指向 |
| 项目级常驻 | 仓库里的 `AGENTS.md` | 该仓库 | 指针：本项目流程真源在 `docs/process/README.md`、适配在 `PROJECT.md`；**不复述细则** |
| 按需注入 | 角色技能 / `docs/process/README.md` / `PROJECT.md` | 派单时或读到才进上下文 | 角色职责、状态机、Gate 格式、属主表 |

插件**替不了**第二层：插件是跨仓库的通用包，只有仓库自己才知道「本项目流程真源在哪」。所以 `process_init` 会保证它存在（只在缺失时创建，已存在则只打印待合并段落）。
