# 单人开发流程总纲（Agent 协作流水线）

> **本文件是流程的唯一真源**：主控上下文被压缩或对话重开后，只读本文件 + `PROJECT.md` 即可恢复流程状态与职责边界，**不依赖聊天历史**。
> **项目适配一律外置到 [`PROJECT.md`](./PROJECT.md)** —— 本文件**只引用、不复述**任何项目专属信息；凡涉及端与目录、命令、产物落点、环境凭据、通知渠道，一律指向 `PROJECT.md` 对应小节。
> **其他文档（含各 README 与角色技能）只允许「最小化说明 + 指回本文件」，不得平行复述流程**。

## 0. 总述

单人开发 + LLM 协作：用 **文件状态机** 代替聊天记忆，用 **裁判 / 运动员分离** 对抗幻觉，用 **Gate** 压缩人力。**主控只编排，不写实现、不写测试、不跑验收。**

四条支柱：① **文件状态机** —— 状态位写在产物 frontmatter，同一时点只有一个权威源，续跑读文件不读聊天（§3 · §9）；② **裁判 / 运动员分离** —— 写实现的人不自证通过，验证角色独立于实现者（§2.1）；③ **Gate 必停** —— 人只在四个压缩点做裁定，其余下放给角色自治（§4）；④ **产物属主** —— 每个文件有且只有一个可写角色，越界即停（§2.3 · `PROJECT.md` §3）。

**不留存 —— 除上述「流程必须」外，一切随批归档**：

> 原则：**流程必须的文件保留，每个需求的都不要**。目的：下一批**干净重新开始**，历史文件不影响新批次，也才能真正验证流程优化。

- **需求专属**（工作区内产生 → 包收口即随批归档 → **不留在工作区**）：`input/**`、`prd/<ID>.md`、`prd/<ID>-design.md`、`prd/<ID>-ui-spec.md`、`contracts/<ID>.md`、`rules/<ID>.yaml`、`bugs/<ID>*.md`、`uat/<ID>-checklist.md`、`prd/*.journal.jsonl`、**原型图目录** `prototypes/<ID>/**`（原型图 + 分层源 + `geometry.json` + `intent.json`，见 §5 UI 几何门禁）、**需求专属测试**（含设备脚本与夹具种子）。具体清单见 `PROJECT.md` §1。
- **过程产物**：`reports/**`（uat / pm / dev / test / review / gaps / 证据 / dev-patches）—— **不含 `reports/_archives/**`（那是恢复源，属保留）**。
- **恢复方式与常驻例外**：上述一切都在批次归档包里（`reports/_archives/`），需要时解包即可，**不留存 ≠ 丢弃**；流程骨架自带的**示范台账与其配对测试**是唯一保留的台账对（用于证明门禁本身可用，见 §6.7）。

**清理原则**：结论进保留文档，过程产物即弃。**复盘的产出 = 流程规范的修改，不是复盘文档**：

- 复盘的**唯一目的**是**优化流程自身**；交付物是**对规范的改动**——落到本文件 / `orchestrator.md` / 各角色技能定义里。**规范改完，复盘文档即销毁**（连同问卷、一手执行台账、交叉核对稿一并进 `reports/` 归档区）。
- **推论**：复盘里凡「该做但没做」的东西，必须在销毁前**转化为规范条款或缺陷单**二选一；**不得**以「写在复盘里了」代替落地。复盘**过程**需要落文件，但落在**过程区** `reports/`（随批归档）；**不新增保留类文档、不占根层级**。

**角色注意**：`reports/` 与 `prd/*.journal.jsonl` 会随角色交付按需重建，这是预期行为；主控在包收口 / 阶段结束时统一清理，角色不必因目录被删而改变交付方式。

## 2. 角色矩阵（硬边界）

| 角色 | 承载方式 | 产出 | 硬边界 |
| --- | --- | --- | --- |
| **orchestrator**（主控） | 本会话主智能体读本文件 + `orchestrator.md` 执行 | 需求核对件、调度、Gate / 交互摘要、状态推进、journal | 不写实现、不写测试、不替人做 Gate 决策 |
| **pm** | subagent（读**同名技能** `pm`） | PRD + 契约 + 设计与说明 + **UAT 清单** + uat 后审核报告 + 功能清单 / 回归基线 | 禁读业务实现、测试、e2e、日志；允许读数据层 schema 与接口路由**签名**（§11.1） |
| **ui-designer** | subagent（读**同名技能** `ui-designer`） | **UI 规格**（`prd/<ID>-ui-spec.md`）：组件判定 / 交互状态矩阵 / 文案定稿；**原型图与视觉数值**（`prototypes/<ID>/**`：原型图 + 分层源 + 几何 + 意图） | **仅触及 UI 的包**；只翻译不发明业务口径；**禁改任何实现源码**、禁读后端实现与前端组件内部实现、不出验收结论；**交付物是原型图（位图），不是 HTML**；不得为了过门禁而改几何 |
| **test** | subagent（读**同名技能** `test`） | 测试用例 + verify 执行报告 + 发布前回归·自动化半 | 只验收 dev 产出物；可读路由签名 / schema / 既有测试；禁读服务实现细节、禁改实现源码 |
| **dev** | subagent（读**同名技能** `dev`） | 实现源码改动 | 禁改测试 / e2e |
| **uat** | subagent（读**同名技能** `uat`） | uat 报告 + 发布前回归·黑盒半 | 扮演真实用户：**不知代码、不知测过什么**；只判「对不对得上预期」；**两段观察**（按 AC 黑盒 + 角色扮演探索，§6.6） |
| **code-review** | subagent（读**同名技能** `code-review`） | code-review 报告 | 只做正确性 / 回归 / 边界 / 可维护性评审；对象 = 发布批次实现 diff |
| **security-review** | subagent（读**同名技能** `security-review`） | security-review 报告 | 只做鉴权 / 越权 / 注入 / 密钥 / 敏感数据评审；对象 = 发布批次实现 diff |
| **logic-review** | subagent（读**同名技能** `logic-review`） | logic-review 报告 | 对抗式逻辑评审：规则→分支映射、未覆盖分支、具体反例；不贴大段代码 |

**落点**：每个角色的**唯一合法写入根**见 `PROJECT.md` §3。主控派单时须把对应行写进任务；执行中发现确需写到表外位置 ⇒ **停下报告，不得自行发明路径**。

### 2.1 三组关键边界

- **test 判「对不对」（自动化断言 + 独立复跑），uat 判「像不像真实用户用起来」（真机 / 功能 / 体验覆盖）** —— 两个角色、两套产物，不是一回事。
- **ui-designer 定「界面该有哪些状态」，uat 判「界面用起来对不对」** —— 前者是 Gate1 的**规格产出**（可观察判据的来源），后者是 Gate4 的**黑盒结论**，不是一回事；ui-designer 不得替 uat 下结论。
- **dev 自测（TDD 内循环）≠ 验收**：dev 跑测试只为让自己变绿；「真绿」由 test 独立复跑确认 —— **裁判运动员分离**。

### 2.2 verify 归属

verify 由 **test** 角色执行，主控只消费报告。命令执行集中到 test，避免「既当运动员又当裁判」。

### 2.3 唯一合法写入根（硬约束）

- 属主表**唯一真源** = `PROJECT.md` §3（角色 / 可写路径 / 禁止）。本文件只写纪律，不复述路径。
- **禁止落点（任何角色一律不得写入）**：① 一次性探针 / 夹具播种 / 清理 / 截图 / 取证脚本落在生产脚本目录 ⇒ 归 `docs/process/tools/<包>/`（§10）；② **未在载体侧登记区登记**的任何新生产脚本；③ 需求专属脚本与快照散落在测试根层或公共夹具目录 ⇒ 归对应的需求测试目录或 `docs/process/tools/<ID>/`；④ `docs/process/` **根层级**（只放 `README.md` · `PROJECT.md` · `orchestrator.md`）；⑤ 任何**未被忽略规则覆盖**的一次性产物（它一定会进人的提交）—— **「用完即删」不构成豁免**：门禁只扫现存文件，抓不到忘了删的。
- **越界即停**：见上「落点」。

### 2.4 禁读边界按信息类型分层

「禁读」禁的是会带偏判断的**业务实现**，不禁校准产出所需的**契约层**（接口签名、表结构）。pm 与 test 的白名单一致（§11.1）；**ui-designer 白名单叠加「既有前端组件的清单与对外 props 签名 / 设计令牌」**（判复用与新增用，**仍禁组件内部实现**）；**uat 是唯一全禁角色**。

### 2.5 并行调度（波次模型）

主控职责：从「串行放行」升级为「**波次调度**」—— 把无依赖的角色放进同一波并行，波与波之间才串行。理由：验证多为小时级，串行放行会让关键路径排成长队。

| | dev(改实现) | test(写测试) | test(复跑) | uat | review 三件套 | pm |
| --- | --- | --- | --- | --- | --- | --- |
| **dev(改实现)** | ❌ 同文件域 | ✅ | ❌ 验证对象须冻结 | ❌ 黑盒前提被污染 | ✅ | ✅ |
| **test(写测试)** | ✅ | ⚠️ 分文件域 | ✅ | ✅ | ✅ | ✅ |
| **test(复跑)** | ❌ | ✅ | ⚠️ 共享构建 / 库锁 | ✅ | ✅ | ✅ |
| **uat** | ❌ | ✅ | ✅ | ⚠️ 同设备互斥；不同设备可并行 | ✅ | ✅ |
| **review 三件套** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| **pm** | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ 分文件域 |

> `code-review` / `security-review` / `logic-review` 均**不在包内流程执行**，移至发布前整体回归（§3.4）。单包收口 = test 独立复跑 + uat + pm 完备性审核。**跨包**：不同包的角色默认可并行（除资源锁）。

**资源锁（主控派单前必须检查）**：**构建通道**（每平台一条，同一时刻每平台仅一个构建 / 单测进程）· **设备**（每台一条，同时仅一个驱动者，占用必须**有记录、有主、有期限**，用完立即释放，到期自动失效）· **本地数据库 / 共享环境**（依赖同一库或环境的角色同波最多一个）· **journal:<ID>**（仅允许单行追加，禁止读-改-写，§7）。具体资源名与占用 / 查询命令见 `PROJECT.md` §2 / §6。

**冲突防护四条（硬要求）**：① **写入域隔离**——每角色只写自己的产物域，禁止跨域写；② **journal 追加安全**——并发只允许单行追加，不得读-改-写整文件，每行必须自带 `actor`；③ **冻结边界**——一旦进入「验证波」，任何改实现源码的角色必须退出该波，否则 test 复跑 / uat 的结论作废；④ **证据唯一寻址**——并行角色的证据必须可唯一定位（`evidence/<ID>/<role>/r<N>/`），不得混放。

**硬禁令（不得以「提速」为由突破）**：❌ 同包 uat 与任何改实现者同波（破坏黑盒前提）；❌ 同包 test 复跑与 dev 同波（验证对象不冻结，结论无意义）；❌ 同一设备并发驱动；❌ 同一构建通道 / 共享库并发；❌ 让同一 role agent 同时处理两个包。

**「复用」与「并行」的关系**：**复用**是**效率取向，不是硬禁令** —— 同一包 + 同一角色，能复用就尽量复用（该包内的返工 / 复跑 / 补测 / 复核 / 收尾修正优先接着原 agent 干，它已有本包上下文）。**允许新建**：① 前一个 agent 上下文已被占满；② **需要独立视角**的复核 / 验收波（裁判运动员分离本就要求换个干净视角）；③ 同包内互不冲突的不同事项要同时推进。**新建本身不是错误**，无需解释、无需停下报告。判断口诀：看「包」不看「角色」—— 同一个包**尽量**复用，不同包就该并行。**计量但不判罪**：每波 Gate 摘要的 `📎 依据` 行报「新建 N / 复用 M」（§4.1），供人观察成本。

### 2.6 主控职责边界

**主控只做三件事**：① **进度安排**（分波、派单、资源锁、Gate 必停、状态续跑、挂起可续跑）；② **给建议**（对方案取舍给出倾向性建议，须标注为「建议」非结论）；③ **分诊与流转**（红灯三类、契约漂移三分、拒收不合规交付 —— 这是编排判断「下一步派给谁」，不是对角色产出的技术复核）。

**硬边界 —— 主控不得自行核实角色产出的技术正确性**：不为了「证明某角色说得对不对」去搜源码 / 读实现 / 查库 / 跑命令 / 逐字比对文档。流程内每个角色产出都有对应核对环节：实现改动 → test 独立复跑；评审三件套 → 发布前整体回归；PRD / 契约 → test 的断言核对；uat → 之后的 pm 验收完备性审核；test 报告 → 交付证据与台账。**正确做法**：怀疑某角色结论时，把这作为核对任务派给流程内对应角色，主控只登记「待核」并排进波次。**唯一例外**：归主控判定的编排动作（拒收不合规交付、恢复被破坏的改动、代跑被拦命令、资源锁冲突裁决）。

**配套一致性修改**：某项变更确定后，把该变更同步到全部受影响处（流程文档 / 调度手册 / 角色定义 / 门禁与文案）一律直接执行，不逐条报批、不问人。**边界**：只许同步**已确定**内容；不得借「配套」之名新增或反转口径、判据、范围、权限、门禁强度；归属不能确定时问人。

**给人类的材料必须以人话为准**：转述角色结论时，必须标明来源角色与「未核对」状态，不得把角色的单方说法包装成已确认事实。

**建议必须标注来源**：任何呈现给决策者的「建议」必须写明提出者 —— `主控建议`（调度视角）或 `<角色>建议`（专业视角）。主控不得以建议形式替人拍定业务参数（阈值 / 金额 / 时限等）：此类参数只能由人给出；若必须先行动，须显式标注「主控暂定值，可一句话改」并登记为待确认项。

## 3. 状态机

### 3.1 状态存放

**状态位写在「当前阶段主产物」的 frontmatter，同一时点只有一个权威源。**

**环节 0（需求核对）——`input/<ID>-需求核对件.md`**：

```yaml
---
id: <ID>
kind: requirement-check
status: draft        # draft / confirmed
gate0: pending      # pending / approved / rejected
flow: full          # full（全流程）/ fast（快速路径）—— fast 不建 PRD、不产生 Gate1 / Gate2
---
```

**环节 1 起——`prd/<ID>.md`**：

```yaml
---
id: <ID>
status: draft        # draft / frozen / red / implementing / uat / done / terminated
gate1: pending       # pending / approved / rejected
gate2: pending
gate4: pending
prdVersion: 1
---
```

> `gate0` **只**记在需求核对件上，PRD 内不重复登记（避免两处权威）。
>
> **触及 UI 的包没有额外的状态位**：原型图与视觉数值是**载体**（`prototypes/<ID>/**` + `prd/<ID>-ui-spec.md` §八），随 Gate1 一并审，**不新增 frontmatter 字段** —— 状态位只记流程走到哪，不记产物有几个。**原型图的验收人只有人**：位图没有机器可读通道，规格 §八 里的字面值就是给人核对的，几何门禁只能替人挡掉「客观可判」的那一半。
>
> `flow` 是**流程分级**的机器可读位（判据见 §8）：`flow: fast` 且 `gate0: approved` ⇒ 状态快照直接给出「直派 dev + 存量回归」，**不再停等 Gate1 / Gate2**；触及 schema / RBAC / 金额 / 对外接口必须退回全流程。省略 `flow` 视为 `full`。
>
> **两处状态位必须耦合**：`status: frozen` ⟺ `gate1: approved`（`frozen` 的定义就是「Gate1 已通过」）。**不得**出现 `frozen` 配 `gate1: pending` 这类自相矛盾组合 —— 两个枚举值域里都含 `frozen`/`pending` 只是**字面重叠**，不代表可自由组合。改状态时**一起改两处**（契约 frontmatter 与 PRD frontmatter 同源，也一起改）。

### 3.2 流转

```text
intake（人给原料 → 主控起草需求核对件） ──Gate0 approved──▶ draft
draft（pm 出 PRD + 契约 + 设计与说明） ──Gate1 approved──▶ frozen
frozen ──test 生成测试 + 缺口盘点（N 绿 / M 红 + 归因）──▶ red
red ──Gate2 approved──▶ implementing
implementing ──快速验证绿──▶ uat
uat ──UAT pass──▶ pm 验收完备性审核 ──▶ 进入 Gate4 停等
Gate4 approved（签收）──▶ 通知槽（可选，见 PROJECT.md §7）──▶ done
done × N ──上线前──▶ release 回归（test 自动化 + uat 黑盒 + 三评审）──▶ 上线

任一步失败 → status 回退 + 建 bug（bugs/<ID>-NN.md）
人裁「不发布 / 终止」 ──▶ terminated（历史全保留，见下）
```

**`terminated`（人裁不发布 / 终止）**：

- **定义** = 包在某环节被**人**裁定**不再推进、不发布**。产物、判据、作废留痕、风险条目、测试用例**一律保留**为「我们查过什么」的证据，**不走**「流程回溯去除」。
- **与 gate 的关系 = 豁免耦合**：`gate1` / `gate2` 等**保留其历史真实值**（如 `approved`）—— 它们记录的是**当时确实通过了**，**不得**改成 `rejected`（那是伪造历史）。`status: terminated` 与任何 gate 值**均不构成矛盾**。
- **必须留痕**：PRD / 设计与说明 / 契约各加变更记录行（触发者 = 人、终止结论、**依据摘要**、**证据落点**），并新增**「终止结论与不可重做理由」**专节 —— 目的是**防止后人重做已被证伪的方案**（含：失败的是哪一环、哪些路已试过、为什么不可行）。
- **不再流转、不清场**：不生成 uat、不做 Gate4、不发通知；台账与测试套件按「**退役但保留**」处置（非活门禁）；产物**原地保留**便于后人查阅「为什么不做」，同时**另存一份耐久归档**（`reports/_archives/`）以防工作区被清。
- **终止 ≠ 可以省掉记录**：越是被终止的包，越要把「**为什么不做**」写清楚，否则等于白做。

**`AC` 变更与包状态的关系（两种情形、处置不同）**：

| 情形 | 判读 | 处置 |
| --- | --- | --- |
| **`AC` 语义变更**（新增 / 改写要求 —— 出现了**未经审批的新要求**） | 已通过的 Gate 覆盖的是**旧对象**，新要求**无人审过** ⇒ 不得沿用 | **`status` 回落 `frozen`** ⇒ **重做判据**（台账 + 测试）⇒ **重判 `gate1`**（必要时 `gate2`）⇒ 才可再进 `implementing`；**闸门字段值一律不涂改**（记「判过的历史事实」）——「现行未判对象 = 新的 `prdVersion`」**写进注记、不写进值** |
| **单条 `AC` 作废**（判据**对象消失**、**无新增要求**） | 包的交付范围**只减不增** ⇒ 旧审批**未被削弱** | **不回退状态、不改闸门值**（与 `terminated` 的「豁免耦合」同理）⇒ 走「确认不做 → 流程回溯」：PRD 标注去除 / `supersede` → 同步台账 → 删 / 改对应测试 ⇒ 红消失；**必须留痕**（三件 + 台账），**不得静默删除** |

> **判别口诀**：问一句「**有没有出现没人审过的新要求**」—— **有 ⇒ 回落重判**；**只是撤 ⇒ 回溯留痕、不回落**。

**前置两环（仅全流程包，见 §8）**：

- **环节 0「需求核对」（Gate0）**：人给的原料**不得直接进 PRD**。主控起草 `input/<ID>-需求核对件.md`：《人的裁定逐条复述（`R-NN`）》/ 端覆盖与落点 / **指代类裁定的参照口径展开**（见下）/ 需求理解 / 待确认项（主控只给标注过的**建议**）/ 明确不做 / 环境与风险。停等人裁定后才允许出 PRD。
  - 属主 = **主控**：核对件的「端覆盖与落点」需全源码可读，而 pm 的读源边界不含服务实现 / 中间件 / 前端页面。
  - **禁止主控替人拍业务参数**（阈值 / 金额 / 时限 / 范围取舍），一律进待确认项。人在核对件上直接改判定的，**以文档为准**（返工 = 改文件，不靠消息）。
  - **「指代类裁定」必须展开参照物**：凡裁定里出现「**与 X 同口径**」「参照 X」「与 X 一致」「同 X 处理」这类**指向另一模块既有行为**的表述，主控**必须**先读源核清 X 的**实际口径**，并在核对件里展开成**可断言判据**（附 `file:symbol` 证据 + 现状矩阵：哪些入口已符合、哪些不符合）。**展开是事实陈述，不是新裁定** —— 不得借展开悄悄加码或放宽原文；展开后发现原文本身有歧义，才升级为待确认项。展开内容须标注「**主控已核实，执行角色不可自读**」，并可用于契约的证据来源。
- **「设计与说明」（Gate1 必审件）**：pm 在 PRD 之后产出 `prd/<ID>-design.md`，把**每一条 `R-NN`** 翻译成设计（落在哪个实体 / 字段 / 端点 / 页面 / 交互）。**落实不了、或与裁定有出入的，必须单列「偏差与未落实项」并给原因**，不得静默略过、不得默默按自己判断改口径；不得在设计与说明里发明新业务口径（需要新口径时回流 PRD 由人裁定）。停点：**随 Gate1 一起审**（Gate1 一次看 PRD + 契约 + 设计与说明三件）。

### 3.3 uat 之后的 pm 审核

`uat ─UAT pass─▶` 不直接进 Gate4，先由 pm 独立审核：

- **定位**：独立子步骤（不是并入 Gate4 摘要），在 uat 之后、Gate4 之前做一次验收完备性审核。
- **审什么**：① PRD 全部 AC 是否被 uat 报告逐条覆盖；② 契约 `alignment` 是否与实际交付一致；③ uat 报告结论是否有证据支撑；④ 有无「未记录 / 未决」项被静默带过。
- **产出与停点**：pm-review 报告（逐 AC 覆盖表 + 覆盖结论 + 遗留清单），属主 pm；pm 审核完成 → 才输出 Gate4 摘要停等。

### 3.4 发布前整体回归（Release Regression）

```text
done（可多个）──待上线包就绪──▶ release 回归 ──通过──▶ 上线
                                   └──未过──▶ 建 bug / 回退相关包
```

- **触发与执行者**：触发 = ① 有全流程包 `done` 且尚未上线，或 ② 距上次发布有新提交（含动了全局入口的快速路径包）；执行者 = **test + uat 双角色**（test 完整跑自动化测试，uat 完整跑真机 / Web 黑盒并照已有功能清单逐功能点），二者结果合并为一份报告。理由：单包回归只覆盖自己那一面，跨包耦合面无人验收；`done` ≠ 可上线。
- **依据**：已有功能清单（全部已上线 / 已完成功能登记表，模块→功能点两级；属主 pm，发布前按当次范围汇总）。每次 release 回归照单跑，防止「改了 A 崩了 B」。
- **产出与门禁**：release 报告（test 自动化结果 + uat 黑盒结果合并，附三评审报告索引），属主 test + uat；人签（复用 §4.1 交互摘要格式），未过不得上线。
- **评审三件套**：`code-review` + `security-review` + `logic-review` 三者**均不作为单包 Gate4 的前置**，在本阶段执行；评审对象 = 本次发布涉及的全部包实现 diff + 规则台账；结论进各自既有证据路径并在 release 报告中列索引；🔴 高危必须修复闭环方可上线。
- **命令与判据**：具体命令槽见 `PROJECT.md` §2；**红即缺口，如实非绿** —— 门禁跑全量存量测试做回归校验，带出历史包未完成红时据实非绿，禁用技术手段掩盖，红的消除只有「完成」或「确认不做 → PRD 回溯去除」两条。

### 3.5 bugs frontmatter

```yaml
---
id: <ID>-01
prd: <ID>
status: open        # open / fixed / verified
relatedCase: <TC>
---
```

dev 修复后置 `fixed` → test 复跑 → `verified`。`bugs.status=open` 时 orchestrator 优先调 dev 修，修完跑三级回归。

## 4. Gate 流程

| Gate | 触发点 | 人看什么 | approve 动作 |
| --- | --- | --- | --- |
| **Gate0** | 主控产出**需求核对件**后 | 需求理解对不对：人的裁定是否被逐条准确复述（有无曲解 / 遗漏）；待确认项是否已全部裁定；端覆盖与落点有无遗漏；明确不做是否写清 | 核对件 frontmatter `gate0: approved` |
| **Gate1** | pm 产出 PRD + 契约 + 设计与说明后（**触及 UI 的包再加 UI 规格 + 原型图**） | ① 验收标准能否写出断言；② 权限 / 边界是否齐；③ **设计与说明是否逐条对上需求核对件的裁定**（有无未解释的偏差）；④ 触及 UI 的包：**UI 规格能否写出用户可观察断言**、组件复用 / 新增判定是否有依据；⑤ 触及 UI 的包：**原型图是否存在、几何门禁是否无 ❌**、视觉数值是否给全（位图没有机器可读通道，只能靠规格里的字面值） | `gate1: approved` |
| **Gate2** | test 产出测试 + 归因后 | 只看断言与归因（红 = 缺口清单），**不看实现** | `gate2: approved` |
| **Gate4** | UAT pass + pm 审核 + 独立复跑绿后 | UAT 报告 + pm 审核报告 + 复跑结果（评审三件套不在 Gate4，见 §3.4） | `gate4: approved` → `status: done` |

**只有人能 approve。主控不得自行放行任何 Gate。**

### 4.1 Gate 与交互摘要格式（**两段式**）

**适用范围 = 主控对人的一切输出**（Gate 停等、进度汇报、中途提问、待裁定件、收口说明）—— **同一个形状**：`✅ 完成了什么` + `❓ 还需要裁定什么`（需要时加一行 `📎 依据`），**不按交互类型换格式**。

停等时**只输出这两段 + 一行依据**，别的一律不写：

```text
【ID】<ID>　<status> → <下一步>　（Gate<N>）

✅ 完成了什么
1. …（人话，1~3 条，每条 ≤ 40 字）

❓ 还需要裁定什么
1. 若只答一条，请答这条：<orchestrator 挑出的最值得质疑的点>
2. 要不要做 X —— <一句依据>
（没有待裁事项就写「无，可放行」）

📎 依据（不进正文，需要时展开）：改动 <n> 个文件（<目录>）｜断言 <+a/-b>｜高风险 <…>｜本波 subagent 新建 <N> / 复用 <M>｜报告 <路径>
```

- **两段都说人话**：代号（缺口号 / 清单号 / 缺陷号 …）只作括注，不得整段只有代号（§6.3）。
- **每条 `❓` 必须能被人直接回一句**（同意 / 不同意 / 选 A / 给个数）。**回不了一句的纯陈述不许放 `❓`** —— 那是 `✅` 或 `📎` 的内容。
- **「若只答一条请答这条」的约定**：`❓` 第一节固定为「若只答一条，请答这条」—— 由主控挑出**本波最值得质疑的一点**（不是最省事的一点）。人若只回一条，就等于对这一条答复；其余 `❓` 视为「未裁定」，主控**不得**替人默认通过。
- **`📎` 固定三件**：① 改动文件数与目录（不列全表）；② 断言变化；③ 本波 subagent 账。**禁止**贴大段代码 / 日志 / 逐文件清单。
- **本波 subagent 账**（**观测项，不判罪**）：本包**新建 N 个 / 复用 M 次**，写成 `新建 0 / 复用 3` 这样的两栏。
- **不许只有一句话的提问**：只问一件事也要写两段 —— `✅` 一行说「已经走到哪一步」，`❓` 说这一问；否则人无从判断该不该答、答了会怎样。
- **`❓` 是给人拍的，不是许愿池**：凡「我打算怎么做」「已知会继续做」的陈述放 `✅` 或说明里，**不许伪装成待裁定项**。

**同形状、三处差异**（其余规则一律相同）：

| 交互 | 抬头 | `📎` | 备注 |
| --- | --- | --- | --- |
| **Gate 停等** | `【ID】<ID>　<status> → <下一步>　（Gate<N>）` | 需要时给 | 再加下方「各 Gate 专项」 |
| **进度汇报 / 中途提问** | 一句话说清在做什么（可与包 ID 并列） | 可省 | `❓` 只列**现在真需要人拍的** |
| **收口说明**（包 `done` / 终止 / 一批做完） | 同上 | 建议给 | `❓` 没有就写「无，可放行」，**不得省略这一节** |

**各 Gate 的专项内容一律折叠进两段**（不再另起方块）：

| 专项 | 落点 |
| --- | --- |
| 共享账号 / 共享库被改动 | **摘要第一行** ⚠ 置顶（改了什么 / 原值 / 恢复方案）—— 唯一允许出两段的行 |
| Gate0：人的裁定条数、待确认项 Q 总数、主控给过建议的条目 | `✅` 末条写裁定条数；**Q 未收敛 ⇒ `❓` 各列一条**（标注「建议非结论」） |
| Gate1：设计与说明 ↔ 需求核对件裁定对齐结论 | `✅` 末条一句结论；**未落实项 / 偏差 ⇒ `❓` 列条**；触及 UI 的包另报 **UI 规格条数 / 不可断言条数 / 无理由新增组件条数**，以及**几何门禁 ✓/❌ 计数与视觉数值是否给全**，有则 ⇒ `❓` 列条 |
| Gate2：红灯归因（基建假红 / 真缺口 / 契约漂移 各几条） | `📎` 一行（含基建假红是否已修复重跑、契约漂移的分诊结论，见 §11.3） |
| 触及数据层 schema（列变更） | `📎` 加一行「列变更 / 补偿 SQL / 回滚」；**`❓` 写「是否同意该 schema 变更」** |
| 切片循环（implementing 期） | `❓` 列待确认 Q 总数与增减（本波 +n / −m） |

### 4.2 Gate 停等时的强制附加项

- **触及数据层 schema 时**，必须列出：改了哪些列 / 是否需数据补偿 / 回滚方式，人显式点头。
- **触及 RBAC / 金额 / 分摊计算 / 新增对外接口**时，标注为全流程事项（§8）。
- **Gate1 摘要**必须附「设计与说明 ↔ 需求核对件裁定」的逐条对齐结论，含**未落实项与原因**。
- **触及 UI 的包**，Gate1 摘要必须附「UI 规格 ↔ 设计与说明」的逐条对齐结论，含**偏差与未落实项**，以及**组件新增的理由是否成立**。
- **通知槽（可选）**：若项目配置了通知（`PROJECT.md` §7），**进入 Gate4 停等时不发**；只在人**签收**（落 `gate4: approved` → `status=done`）的同时发一次。**签收后已无待裁定 ⇒ 通知内容只保留「完成了什么」一段**（该段留空显示「无」）。**拿到回执 ID 才算本包收口**；发送失败必须如实上报，不得静默跳过。

## 5. 命令集

**命令槽的唯一真源 = `PROJECT.md` §2**（用途 / 命令 / 说明四栏），至少覆盖四类：**快速验证** / **产物落点门禁** / **台账门禁** / **journal 追加**。本文件不复述具体命令。

**框架自带脚本**（随框架版本化；**实际路径与调用方式以 `PROJECT.md` §2 为准**，脚本的项目专属配置登记在 `PROJECT.md` §4 与 §5）：

| 用途 | 说明 |
| --- | --- |
| **journal 追加** | 锁 + 指纹校验 + 原子替换；**禁止手工读-改-写**（§7） |
| **台账门禁** | 校验台账与测试用例双向配对、测试 import 白名单、`prdVersion` 一致性（§6.7） |
| **落点门禁** | 按 `PROJECT.md` §3 属主表 + `PROJECT.md` §4 登记区判定「会进下一次提交」的未跟踪文件落点（§2.3） |
| **UI 几何门禁**（含 **⑩ 项目令牌一致性**：配了「UI 项目令牌」就要求**画面主色**全部能由该色板推导出来 —— 只管主题层，小字/描边/图标用色由 ⑧ 兜） | 判「界面摆得对不对」里**客观可判**的那部分：① 几何确实来自产物 ② 不溢出画布 ③ 文字不重叠 ④ 同列不过挤 ⑤ 声明的居中真的居中 ⑥ 内容区边距对称 ⑦ 网格符合率（⚠）⑧ **文字对比度**（WCAG，从产物像素采样）。加 `--verify` 会**重导一次逐元素比 bounds**，把「测量来自产物」从声明变成验证 |
| **版本同步** | 同步 PRD frontmatter `prdVersion` 与测试头标注，防漂移 |
| **UAT 前置自检** | 派单给 uat 之前跑一次，确认「环境 + 验收账号 + 目标端点 + 清单」就绪；不通过即退回，不得靠空转等待（配置见 `PROJECT.md` §5） |

**判据口径（硬约束）**：

1. **快速验证的判据 = 「本次验证无红」**：任何一段报红即如实上报，**不做「存量红 / 新增红」分账**。
2. **红 = 缺口；禁止用技术手段掩盖** —— 白名单 / 排除用例 / 改比对器 / 取错退出码等一律禁止。
3. **禁止裸管道掩盖退出码**：凡以管道收集输出，必须启用 `pipefail`（或改写为 `cmd > f 2>&1; echo $?`），否则不得用该次退出码作红绿判据。
4. **历史遗留要放行时一次一议**：当场在 Gate 摘要里写明「哪一段、哪几条、依据是什么、由谁点头」；**禁止**落成永久白名单或永久台账。**恒红的门禁项必须修掉或显式豁免**：任何跨多轮恒红的静态检查项，必须在合理期限内修复或显式加入豁免，不得长期红着。
5. **命令段数以项目声明的命令槽为准**：凡文档列出的命令与项目实际不一致时，**以 `PROJECT.md` §2 为准**，并回来修正本节。

> **UI 几何门禁的两条口径**（`check-ui-geometry`；路径与调用以 `PROJECT.md` §2 为准，阈值登记在 §4）：
> ① **测量必须来自产物** —— `geometry.json` 的 `bounds` 只能由适配器从产物导出。`source` 只是**自述字符串**，编一个看起来很专业的它就能过，**所以它不构成证据**；真正的证据是 `artifact` 指向的产物**真实存在**（不存在即判 ❌），再加 `--verify` 重导一遍逐元素比 `bounds`。
> ② **意图由人声明** —— 哪些元素「应当居中」、内容区横向带在哪，属于作者意图，写在 `intent.json` 里。**工具测量结果与作者声明意图，两者不得互相冒充**。
>
> **⑧ 对比度为什么笨到去采像素**：图层颜色 `info` 根本不提供，只能从**合成结果**采样 —— 而人看到的正是合成结果。**小字的对比度必须留余量**：12px 中文笔画只有 1px 宽，渲染出来连通像素都被抗锯齿冲淡，名义上 4.63:1「刚够」的配色，**实测最亮像素只有 3.9:1**。这条在真实项目上复现得很干净：规范给的次要文字色按标称算 **5.42:1**（达标），**12px 渲染实测只有 ≈4.13:1**（不达标）——**差约 1.3，标称达标 ≠ 渲染达标**。所以 **12–13px 不要用次要档，直接用主文字档**；判据一律以 ⑧ 的渲染实测为准，别拿标称值去和阈值比。
>
> **⑩ 项目令牌一致性管到哪**（别把它的绿当成"全都合规"）：配了 §4「UI 项目令牌」后，⑩ 从令牌源抽出色板，要求**画面主色**（占画布 ≥0.5% 的）全部能由它推导出来（允许色板内两色按任意 α 叠加）。它抓的是**「用了整套别的色板」**这种主题层硬伤 —— 实测把深色默认主题配浅色项目规范，⑩ 立刻点名 `#161b22`（56.7%）。**占比更小的色（小字 / 描边 / 图标）它不管**，那由 ⑧ 兜。**两者是分工不是替代：⑩ 管「用没用你的色板」，⑧ 管「这个色看不看得清」。**
>
> **⑨ 也有能力边界**：它重跑适配器再比 `bounds`，证明的是**「测量来自产物」，不是「测量像素级准确」**。实测适配器对同尺寸的卡可能报同一个 `bounds`、实绘却差 1–2px（`info` 报 `[246,y,1164,h]` ⇒ x1=1409，实绘边框在 1407）。这类偏差 ⑨ 看不见，⑥/② 已按「适配器偏差带」区分**测量偏差**与**设计走样**。
>
> **⑧ 与 ⑩ 都在工具链不可用时优雅降级为 ⚠**（不判红），但 **「文字与背景完全同色」除外** —— 那是最严重的失败（1:1），会逐像素复核后判 ❌。实测它抓到过「整条状态栏被导航栏底板盖住」：作者在图上看不出来，报告里还写了"状态栏已画"。
>
> **建议 Gate1 之前那次门禁调用带上 `--verify`**（日常自检可以不带）：它是唯一能把「几何来自产物」从声明变成验证的一步。`--verify` 拿不到适配器时**直接失败**而不是静默放行 —— 人明确要求了验证，做不到就必须说做不到。

> **多屏**：一个包通常不止一屏，所以几何文件支持 `geometry.json` 与 `geometry.<屏幕名>.json` **并存**、逐屏判定；每屏的作者意图优先取同名的 `intent.<屏幕名>.json`，取不到才退回共用的 `intent.json`。**「一包一图」是例外，不是常态。**
>
> **项目自己的设计规范目录也要登记进 §3**：真实项目通常有 `docs/design/**` 这类目录，模板 §3 覆盖不到 —— 不登记就会被落点门禁判越界。

> **整个 UI 工具链都是可选的** —— 本节只规定「有界面就得能量」，**不规定用什么工具量**（工具选型是实现细节、不是流程判据）。没有可用工具时，按 `prd/_UI_SPEC_TEMPLATE.md` §8.0 声明「不使用」并说明理由，同时**把视觉结论交回人裁**（审美终局本来就只有人能判）。
> **门禁判不了的**：好不好看、风格是否合适、动效是否顺 —— 这些一律留给人在 Gate1 / Gate4 上裁。

## 6. 产物属主与纪律

### 6.1 产物属主与时机

**属主表唯一真源 = `PROJECT.md` §3**（角色 / 可写路径 / 禁止）。本节只定义**纪律**：

- 每个产物有且只有一个属主；**属主不同时的同步顺序**由主控在派单里一次列全「需同步的副本清单 + 各自属主 + 责任人」（§6.4 第 11 条）。
- **过程产物默认不进版本库**（由项目的忽略规则决定，见 `PROJECT.md` §3）；因此**就地覆盖 / 折叠即不可恢复** —— 压缩超限报告前，**必须先把原文按 §1 打进归档区（打包 + 清单 + 校验和）再改**。
- `rules/<ID>.yaml` 骨架由主控起草、test 维护；台账是**机器可读镜像**，文档与台账冲突时以台账 + 测试为准（§6.4 第 11 条）。
- **PRD 版本漂移检测**：test 在用例头强制标 `@prdVersion N`（与 frontmatter `prdVersion` 一致）；台账门禁校验不一致即 ❌。任何 `prdVersion` 变更必须同时过「版本同步」脚本。

### 6.2 AC 可验证性设计

**规则：pm 出 AC 时必须自带可验证性要素，否则 test 有权拒收。**

| 缺口类型 | 典型形态 | 为什么验不出来 |
| --- | --- | --- |
| **探针不足** | 秒级判定 | 边界点的秒位恒为 `:00`，新旧实现在这些点取值完全相同 ⇒ 断言存在却探不到 |
| **平台差异** | 桌面 / 真机序列化差异 | 两个运行时的 JSON 库对空值返回不同字面量 ⇒ 单测环境恒绿、长期无人发现 |
| **口径缺失** | 时间窗判据 | 只写「含端点」未写「秒级」⇒ 实现按分钟粒度多年无人发现 |

1. **边界四要素**（凡涉及阈值 / 时间窗 / 数量上限的 AC）：**内一点**（应通过）、**外一点**（应拒绝）、**两端各一点**（闭区间）、**两端外各一秒 / 一单位**（应拒绝）。四要素缺一即判 AC 不合格。
2. **判定粒度显式**：写清「分钟级 / 秒级 / 毫秒级」，禁止只写「含端点」。
3. **平台差异声明**：凡依赖运行时行为（JSON 库、文件系统、时区、编码、原生 API、内存模型）的 AC，必须写明「桌面 / 单测 与 真机 行为是否一致」；不一致的，用例必须含能在桌面环境抓住它的判据，**不得只写行为断言**。
4. **数值口径**：涉及估算 / 换算的，写明是「实测值」还是「估算兜底值」。**阈值类判据必须自带「可分辨性」** —— 凡**门限 + 统计量**（中位数 / 比例 / 分位）的 AC，**必须**至少写明其一，否则 **Gate1 不得放行**：① **最小样本量 / 最小重复次数**；② **「测量步长 < 判定余量」的证明**（写明余量是多少、**剔掉一条读数会让统计量移动多少**，以及两者的可断言倍数关系）；③ **两者都给不出 ⇒ 不得作为停点判据**（只能当**观察项**，**不得据此放行或拦截**）。

### 6.3 代号可读化

各类流程代号（缺口号 / 清单号 / 缺陷号 / 判据号等）只是流程内部的追索键，本身不携带任何含义。**违反本条按返工处理**，不视为「表述风格」问题。

1. **首次出现必须写「人话名（代号）」** —— 人话名 = 一句话说清「谁、在什么场景、看到或发生了什么不对」；禁止「确认卡问题」「某某号相关」这类同义反复。
2. **清单必须自带说明** —— 缺口 / 缺陷 / 待办清单除代号外必须有人话说明；禁止只列代号的清单。
3. **汇报正文用人话，代号只作括注** —— Gate 摘要、复盘、结论、对人汇报正文一律用人话，代号放括号里供追索。
4. **命名与登记同时进行** —— 新条目进缺陷单 / 缺口登记时没写人话名不算登记，orchestrator 有权拒收。
5. **存量靠对照表，不改写历史** —— 历史条目原文与**已落盘的文件名**都不回改（只追加）；存量代号的可读含义集中在「代号对照表」，新代号产生时同步追加一行。
6. **给人看的摘要必须能独立读懂** —— 禁止在正文里出现未解释的代号；禁止让读者为了看懂摘要去查表。
7. **中文短名是产物的第一可读标识** —— 每条 `AC-N` / `E-N` / `U-NN` 都必须有一个 **6–12 字中文短名**（取材于该条标题句的主干，不是照抄全句），并在两处强制落地：**文件名** `<中文短名>-<代号>[_序号].<ext>`（若完成度门禁只认 ASCII 前缀，写成 `U-NN-<中文短名>.<ext>`；禁止 `<代号>-<英文 slug>.<ext>`）；**正文引用**写 `中文短名（代号）`，同一份件内跨小节再次出现时**必须重补一次短名**。
8. **机器解析的前缀不得中文化** —— 被门禁正则读取的片段（用例名前缀、边界号、版本标注等）保持 ASCII；中文只进「短名段 / 说明段 / 文件名后缀段」。动前缀即伤门禁与引用链。
9. **短名一处定死、全链复用** —— 短名在 PRD 该条标题内一次定义（形式 `AC-N <中文短名>｜<完整判据句>`），下游一律照抄：台账的 `ac_name` 字段、契约、uat 清单判据索引的短名列、测试的 `describe` / `it`、报告、证据文件名。禁止各写各的别名。

> **自查一句话**：把这段文字发给没参与本包的人，他能不能看懂？

### 6.4 断言与判据纪律

1. **「权限类断言实跑律」** —— PRD / 契约里每一个「权限类可断言点」必须① 存在同名用例 ② 必须有一次实跑记录。二缺一即视为未验证。
2. **台账的 `expect` 字段不是证据** —— 禁止仅凭 `expect: green` 判定某权限点已就绪。台账与实跑不一致时，以实跑为准并登记台账错误。
3. **权限类断言的取样点必须在「令牌身份 ≠ 请求身份」的错位处**：仅用同一身份发请求的断言证明不了任何鉴权 —— `403` 可能来自与目标机制无关的原因，删掉目标校验仍然绿。
4. **禁止把漏洞行为写成回归锁**：任何断言以「以 A 的令牌、B 的身份操作 → 成功」为期望的用例，必须先确认该行为是否合法；未确认前不得进入回归基线。**反例登记**：自称「判别用例」但删掉被测机制仍能通过的用例，一律标 `假绿`。
5. **新增 / 修改权限相关机制的包，必须做「身份来源并集核查」**：穷举全部从请求体 / 查询参数取调用者身份的端点，不得只修被报告的那一个。
6. **「冻结断言自相矛盾」是 dev 的强制停止条件**：当 dev 发现两条已冻结断言对同一形态给出互斥期望时，必须停下来打回 test / pm，**禁止**用「同时满足两套断言的最小判别式」绕行。同源第二形状：为响应攻击链而把校验做得比裁定更严，同样会收紧到不可用 ——「收紧到不可用」与「放宽到不安全」是同一枚硬币两面，都必须由判据决定。
7. **裁定改变某行为时，必须穷举该行为的全部受影响副本** —— pm 侧核对旧判据、test 侧同步旧断言：**pm 侧（变更前，先做）**任何 `prdVersion` 变更落笔前，先逐条列出**受影响的既有 AC / Then 句**，核对是否被新判据**推翻**，被推翻的必须在**同一版内显式改写并加注**；**test 侧（变更后）**断言改动前先搜目标字段 / 端点，列出全部断言点 → 逐个判定「锁定的是旧口径还是新口径」→ 逐条同步并在报告中列出清单。**承接点下沉，不得给数据打补丁**：既有断言被推翻时，应把它要守的性质**下沉到不受新判据影响的更稳层**去断言；**禁止**为了让旧断言继续成立而修改数据或加特判 —— 那是编造。
8. **「必须可测」的契约条款，同一行必须给出测试侧可达的 import 路径**：紧邻处写明该入口从哪个「已被测试门禁白名单放行」的模块可达。
9. **台账 `expect` 必须有 `pending_ruling` 态**：口径未定、但已被写成断言的判据，台账标 `pending_ruling` 而不是 `red` —— 不计入红灯、不阻断放行、不产生 dev 返工，报表中必须与「真缺陷红」分列。台账的红至少分四态并在报表分列：`red`（真缺陷，须修）/ `pending_ruling`（口径未定，不阻断、不返工）/ `flaky`（已登记签名的一次性 I/O 抖动，须附签名与复现次数）/ `withdrawn`（裁定后作废）。`todo`（已写、未跑）必须带预期（`expected: green｜red`），复跑前先写下预期分布、跑完如实记（不符合时不得事后改预期）。预登记预期必须绑定「被验证对象的指纹」（源码哈希 / 提交 / 标签），指纹变了 ⇒ 预期自动作废、须重新预登记。
10. **「需求去除 / 取代」必须在派单时列全「需同步的副本清单 + 各自属主」**：① 确立单一权威源 = 已冻结的 AC / 契约判据，其余副本一律向它对齐；② 派单时给出副本清单表（副本 / 属主 / 是否需改 / 责任人），并为新建副本指定同步责任人；③ 「权威源 = 文档」若不可机检，则事实上唯一被执行的权威是**台账 + 测试** ⇒ 把台账视为机器可读镜像、增加一致性机检，顺序固定为「先改台账，再改文档」。
11. **「副本清单」必须包含「位置引用」，且现状证据只认符号不认行号**：① 现状证据一律以符号 / 构造定位，行号只作 `as-of` 附注；② 跨包同改一个文件时，把「刷新引用该文件行号的文档」列为副本清单的一项（属主 = 各包 pm）；③ 机检建议：台账检查增加「引用的 `file:line` 是否仍包含所声称的符号」。
12. **验收前置必须核对「设备 / 环境上跑的是本次改动构建的产物」**：UAT / 真机验收开始前必须记录并核对被测产物的构建时间 / 版本号；改动后必须同步重打包 / 装机再进验收；UAT 报告须写明「所验产物的构建时间 / 版本」。出现「改了却毫无变化」时，第一嫌疑是产物没更新，而非代码没改对。
13. **「缺口」判定若依赖跨对象 / 跨包外推，必须先以问题形式提交，不得直接记为缺口**：任何「缺口 / 缺陷 / 应改」判定，若依据来自跨对象或跨包外推，必须先标注「适用范围待确认」并以问题形式提交，不得据此派出实现任务。**同一纪律适用于「事实性转述」**：转述他人给出的**事实性结论**（数值、因果、断言语义、代码行为）前**必须先核一手来源**；核不了的**标注「未核对」**。
14. **被引用包的判据，其数值字面不得在被引用包之外出现第二处；勘误必须带机器可识别标记**：承载断言的引用必须同一行带 `（引自 <ID>）` 标记；默认「标注」，不默认「删除」—— 宁可多标，不可误删。
15. **出正式基线前必须把「资源独占」确认为可核查事实；一次性探针必须自毁**：① 出基线前先确认真实独占（枚举并清理非当前验证者的写库进程）；② 一次性探针必须自毁（超时兜底 / 派单时登记 PID）；③ 清理函数禁止按宽泛条件全删，必须按精确标识定点清理。
16. **错误码判别约定**（项目可在 `PROJECT.md` §1 收紧）：`403` = 无权访问该资源，`409` = 有权但此操作对任何有权主体都不允许，`400` 只留入参非法。**两步判别法**（先判访问权、再判规则）：① 该主体对本资源是否本来就有访问权？无 ⇒ `403`；② 该操作对「任何」有权主体是否都不允许？是 ⇒ `409` + 明确 `message`。**可操作探针**：换成拥有同等权限的另一个合法主体重试 —— 仍被拒 ⇒ 非越权 ⇒ 应 `409`；换主体后成功 ⇒ 身份相关 ⇒ `403`（⚠️ 此探针有盲区，必须回到第 ① 步先判访问权）。**越权与状态同时成立 ⇒ 先判越权**（`403` 优先）；`403` 的 `message` 必须附「如何获得权限」的指引。
17. **「通过」所引证据必须与被断言的「端点 + 时点 + 身份」三者一致**：三者任一不符 ⇒ 该结论不成立，须补测。pm 的验收完备性审核必须逐条比对引用证据的端点与出参。
18. **被测环境必须由主控托管**，禁止由角色 subagent 作为其会话内后台任务启动：凡被后续角色依赖的长时间运行环境，一律由主控以自身托管后台任务启动，并在派单里写明「由谁持有 / PID / 启动时间 / 如何确认存活」；角色发现环境不在 ⇒ 急停上报，不得自行重启后再测。主控代跑的进程须显式标注，其结果只作附录。
19. **「当前状态一览」置顶**：凡活跃需求包文档（需求核对件 / PRD / 契约 / 设计与说明）必须在**文档最顶部**放一节「当前状态一览」—— 一屏内可读完、只写「现在是什么状态」、不留沿革、随每次交付就地更新。① 它是该文档当前事实的唯一权威，与正文冲突时以顶部为准；② 至少含：交付状态 · 预期红绿 · 未决事项 · 最后更新轮次；③ 更正块体例继续保留，但不得再被当作当前事实源。
20. **「写红」必须早于「实现」落盘，且被测不冻结不得定色**：① 凡新增 / 收紧判据，「写红」波次必须在实现落盘之前完成，并留存一次「全红存档」，否则该用例的判别力不可证明；② 同波并行时若无法保证「写红早于实现」，则该波不得定色（定色须等被测对象冻结后下一波复跑）；③ 禁止用必然变绿的手段冒充覆盖 ⇒ 属假绿，应挂待办 + blocker 如实标注。**「实读义务」**：任何关于「现状是什么」的陈述都必须以「实读源码 / 台账 / 证据 / 真机记录」为依据，禁止以推断代替实读；写推断时必须明标「未实读、系推断」，且该推断不得作为判据、不得进入任何红绿结论。**判别力自证义务**：用例须能回答「未实现态下它是否会红」，test 应在报告中给出判别力自评。**验收标准**：「写红存档」的达标标准 = 「核心缺口点为红，且红因正确（非装置错误）」，不是「全部为红」；必须保留「现状即绿」的锁定项（`expect: green` / 「锁定项」标注）—— 它们防实现方跑偏，恰恰不能删。
21. **代码与流程文档均不得记录流程元数据与来龙去脉；碰到即就地修正**：① **禁新增** —— 实现与测试代码的注释里不得出现需求 / 单据编号、裁定编号、波次轮次、票据号、`docs/process/**` 路径、技术债条目号（注释只描述代码自身的 WHY；测试文件中用例编号属用例自身命名 ⇒ 可保留）；② **碰到即修** —— 改动某文件时若发现此类注释，必须就地修正（剥掉编号 / 路径 / 轮次，保留其「为什么」），不要求跨文件扩查；③ **修正 = 零行为改动**（修正后的 diff 中非注释行变动必须为 0）；④ **不做专门的历史清理包**，以「碰到即修」渐进收敛；⑤ **保留标准** —— 真 WHY 必须留：非显然约束、平台坑、安全理由、反直觉设计的原因、字段语义、跨模块不变量、停用功能的根因与恢复步骤；⑥ **流程文档同样适用（只记规范，不记来源与归因）** —— 流程文档只写三类（规范条款 / 通用理由 / 条款效力），**禁写五类**：来源（时间戳溯源、来自哪个包 / 哪一轮 / 谁的提议）、事故归因、人的原话引用、事故细节（增删行数、命中数）、**需求过程内容**（包 ID / 批次名 / 批次专属命令）。**追溯的归属地是提交信息与历史记录**；归档原文不回改。
22. **「日志 / 控制台干净」类断言必须写明观测窗口**：① 写明窗口（如「常规路径」/「停止时工具在途窗口」/「全时段」）并在报告中给出定义；② **不得**用窄窗口的「命中 0」表述为「全窗口无异常」；③ 本条只约束表述与判据口径，不要求一次性消灭存量噪音。
23. **机器能证的部分先证完，只把真正只能人判的部分留给人**：① 提「待人确认」之前，必须先把机器能证的事实穷尽（结构、样式、尺寸、文本、接口 / 日志读数等），并把判据**回指需求原文**，据此把待确认项**收窄**为「真正只能由人判」的部分（观感 / 审美 / 严重度 / 业务取舍）；② 条目里必须写清「残留的到底是什么」—— **不得**把机械核对推给人，**也不得**反向用机器证据把人判项改判为通过；③ **未受证的证据不得留档** —— 截图 / 读数必须与**状态同步采集**，事后补拍、无法证明当时状态的证据一律删除。
24. **写库型验证的两条硬约束**：① **幂等 / 无副作用断言必须比集合** —— 必须比对对象集合的成员与行数前后差异（差异必须为空），不许只看代表行的字段；② **独立复跑必须锚定干净状态** —— 用例自身会写库 ⇒ 复跑报告必须记录起止时间戳并声明「运行期间无并发写活动」（或如实说明不确定），有并发副作用时该次结果不得作为定论。
25. **验证必须声明「它跑在哪个基线上」**：① 每份验证报告必须写明运行起止时间戳 + 所跑源码基线指纹（工作区文件清单 + diff 统计，含未跟踪新文件）+ 关键库状态；② **冻结后统一重跑** —— 队列做完 ⇒ 冻结 diff ⇒ 由 test 在**冻结 diff** 上重跑一次 ⇒ 只有这份结果可背书发版；③「跑在旧基线」的绿 ≠ 对当前 diff 的绿。
26. **报总数 / 规模的聚合不许带 `LIMIT`**：① 凡用于「报总数 / 报规模 / 报条数」的查询不许带限行；② 若必须限行展示，总数必须用另一次不带限行的计数单独取；③ 严禁把被截断的结果当作总数上报。
27. **验证报告必须按包列明「覆盖哪些文件」**：① 禁止用某个检查命令的「绿」暗示它没覆盖的包 / 文件也已验证；② 结论按包分别写（不得合并成一句「门禁全绿」）；③ 失败按文件归因并与工作区状态对照，区分「本次引入 vs 既有」，不得用切换版本状态的方式做对照；④ 既有整仓红若不作门禁，必须在报告里作为事实写明。
28. **判据与证据不得依赖夹具主键**：① 判据 / 证据一律以「夹具名称 + 可观察行为」为准，禁止把夹具主键写进判据正文、用例断言、验收步骤或报告；② 主键只允许出现在原始证据快照里，作为可回溯记录，不作判据；③ 脚本一律按名称解析夹具，不得写死 id。
29. **断言必须能探到它声称要探的那件事（载体可失败性）**：① 任何载体 / 脚本 / 探针 / 断言必须有失败路径（真伪判定 + 非零退出码），只落盘、永不非零退出的脚本等同静默免检，不得计入覆盖；② 报「绿」必须附「它怎么才会红」—— 反向对照 / 元负控（含注入一个故意有缺陷的实现）是最低成本的证明；③ 禁止六类「探不到」的断言：**不能失败 · 只断后态 · 绕过被测主体 · 存在性代理 · 前缀包含 · 引用尚未落盘的标识符**；④ 判据字面取不到时，先排除「判据文字 / 选择器本身有误」再判红；⑤ 产物级验证必须用行为 / 字面量，不能用标识符名。
30. **模型参与判据的采样与结论强度**：① 模型参与的输出属概率性 ⇒ 每条模型相关判据**至少独立重复 3 次**，涉及诱导 / 未绑分支 **≥5 次**，**1 次违反即不通过**（不得取多数）；② 必须附样本量与命中率，无样本量的「通过」不予采纳；③ 结论强度必须诚实标注 ——「样本内 0 违反」≠「残余已归零」，须给漏检概率说明；不加码采样时须写明「本证据不足以回答低频残余是否仍存在」；④ 观察项与判据探针必须分离，不得用观察项替代或加强判据结论；⑤ 残余风险只能由人裁定接受。
31. **编号命名空间：勘误与边界必须分号**：勘误号（`ER-N`，只追加）与边界 / 异常号（`E-N`）不得共用；被用例名引用的命名空间不得改动；跨件引用必须带件名；改名只动编号 ⇒ 不升 `prdVersion`；历史报告不追改，在件尾加命名空间注。
32. **「判别力自证」不得把被改对象的当前（未修）状态当作不变量**：① 反例形态 —— 自检断言「live 仍处于改造前的红态」，而同一装置的判据断言相反 ⇒ 逻辑上不可同时成立；② 后果 —— **修好缺陷反而使自检变红**，这不是自检，是**给缺陷下的一道冻结令**；③ 正确形态 —— 自证必须建在**合成夹具 / 内存变异**上（`mutated !== live` + 变异后翻面），`live` 只作变异基座与同向对照，不得断言其当前取值；④ 一次只变一个因子，需同基座隔离变量；⑤ 发现即修 + 枚举同类，且必须声明枚举面；⑥ **判据不得为迁就自检而放宽**（真判据优先，自检让位）；⑦ 变异基座必须取「修复前后都存在」的**稳定锚点**，或改用合成夹具、不读 live。
33. **清理装置必须自证「清理后残留 = 0」**：① 清理装置失败时必须报错，不得静默留下脏数据；② 各步必须彼此独立（每表各自兜错，不得一步失败让其余全跳过）；③ 结束时必须按签名兜底清扫，不靠内存里的 id 清单；④ 必须硬断言残留 = 0，否则判红；⑤ 签名列被截断时须改从未截断的列反查；⑥ 交付必附「跑前 / 跑后」两次读数；⑦ 「残留 = 0」必须写清口径 —— 区分「本包签名在库中的残留」与「全局测试基建的既有写入」。
34. **判据的落点纪律**：① 判据必须落在「失败实际可发生的那一层」；② 结构性判据不得单独承载「功能可用」结论（「接线存在」与「功能可用」是两件事，后者必须由行为级判据承载）；③ 登了「受控实验」的判据必须有可执行载体，否则视同未登记；④ 判据不得比它自己的文档更严（文档声明的等价写法必须有自证证明被实现接受）；⑤ 判据也会约束实现结构 —— 挡住重构时不许「顺手放宽」：报告冲突、由判据属主重审，禁止静默放宽判据，也禁止静默改变语义。
35. **过程产物的写入安全（硬约束）**：① **先校验后写入** —— 禁止对目标文件「先截断再校验」；② **必须经临时文件 + 原子替换**，写失败时目标文件必须保持原样；③ 适用范围 = `docs/process/**` 全部过程产物。

### 6.5 三级证据模型与证据体积

| 层 | 内容 | 形态 | 入库 |
| --- | --- | --- | --- |
| **L1 结论** | 角色报告 `reports/<role>/<ID>.md` | 单文件、人读 | ✅ 必入库 |
| **L2 摘要** | 每包一个累积文件，每轮追加一条记录（轮次 / 角色 / 命令 / 结果 / 耗时 / 证据指针） | 单文件累积 | ✅ |
| **L3 原始** | 原始回显、截图、会话导出、探针时间线 | 按 `evidence/<ID>/<role>/r<N>/` 分目录 | ❌ 包 `done` 时打包归档 |

| 体积与产出规则 | 内容 |
| --- | --- |
| **产出粒度** | 一包一个 evidence 目录；每场景一份 `summary.json` + 必要原始回显；不为每个探针 / 每次轮询单独落文件 |
| **可复现 vs 不可复现** | 不可复现（原始回显、截图、会话导出）→ 保留；可复现（脚本产物、生成夹具）→ 由脚本重建，不入库 |
| **大文件 / 禁止落证据** | 大体积原始会话导出压缩后入库；编译缓存与夹具生成目录等中间产物禁止落证据 |
| **包 `done` 后 / 体积红线** | evidence 目录打包为单个归档（原目录删除），报告路径引用随之变为「同名归档」；单包 `reports/` ≤ 20 个文件且 ≤ 2MB、单份报告 ≤ 300 行、单份证据文件 ≤ 200KB，超限只留摘要 + 结论 |
| **默认产出四件** | 每包默认只产：包文档（PRD + 契约）/ 规则台账 / **一份累积报告** / journal 单行；其余（分轮报告、探针脚本、截图、时间线）**按需产出** |
| **单文件累积** | 同类报告只写一个文件、往后追加，**禁止每轮 / 每角色各建一份**；时间线 / 日志类一律累积单文件 |
| **过程产物不入库** | 版本库只收规范（本文件 / 项目适配 / 调度手册 / 模板）；其余由忽略规则排除 |

> **红线**：禁止为每一轮 / 每个探针各建一个文件 —— 同类产物必须累积进同一文件或打包归档。

### 6.6 缺口收集窗口与批量修 / 验

**通用理由**：缺口若串行发现，每发现一个就要跑完整条链，而修复常是分钟级、验证是小时级 ⇒ 分批发现会重复付出整条链的代价。

**机制**：验证阶段（test 复跑 / uat / review）发现的缺口**不立即触发修复**，而是由 orchestrator 登记入缺口清单 `reports/gaps/<ID>.md`；达到窗口关闭条件后，一次性派 dev 修全部，随后一次重构建 + 一次验证。

- **窗口关闭条件**（满足其一）：① 当前验证轮次自然结束；② 清单累积到 ≥3 条；③ 在 Gate 前要求收口。
- **必须立即修、不进窗口的例外**：① 阻断性缺口（导致后续验证无法进行）；② 安全红线（越权、数据泄露、注入、密钥外泄）；③ 会使已得验证结论失效的缺口；④ 明确要求立即修的。
- **清单格式（一行一条）**：`编号 | 来源轮次 | 人话说明 | 分诊 | 目标角色 | 是否阻断 | 状态`。
- **纪律**：分诊归 orchestrator；清单不改变「红不得掩盖」原则（缺口仍须显式登记，不得静默关闭或静默延期）；批量修完后的验证必须逐条覆盖清单全部条目（禁止「修了 5 条只验 2 条」）；逐条必须有人话名（只有代号的清单视为未登记，orchestrator 不收）；窗口期内的 Gate 摘要必须附清单（共几条、是否含阻断项、预计几批修完）。

> **uat 双段观察**：uat 报告**必须分两段** —— ① **按 AC 逐条黑盒观察**；② **角色扮演探索**：选定**一个具体身份 + 当天一个具体任务**，只带着这个任务去用（登录 → 干活 → 交接这类完整链路），并在真实现场条件下走（断网 / 弱网 / 遮挡 / 中途切走 / 杀进程再开），沿途任何别扭时刻都要记下来，**哪怕它不在任何 AC 里**（照抄界面文案原文）。**禁止「乱点」** —— 无意图的随机操作不产生可用结论。第二段结论**不是判据、不判通过与否**，是**立项素材**，且**必须单列成节**（标题「AC 之外的新发现」）；**「未发现」也是有效结论**。配套：pm 的 uat 后审核加一张「操作 × 恶劣前提」矩阵，**空格子标「未承诺面」并上呈**。

### 6.7 测试分层与门禁范围

**入库（常驻）只有三类**：① **通用 / 跨需求测试**（与单个需求无关的长期测试）；② **不变量测试**（产品核心规则的长期守卫，**不得带 `@prd` / `@prdVersion` / `@case` 标签**，标签才是与台账的耦合）；③ **曾抓过 bug 的用例**（文件头注释登记来源即可，同样不带 `@case` 标签）。外加公共基建：测试辅助函数、全局 setup、账号种子，以及**唯一保留的示范台账 + 其配对测试**。

**不留存（随批测试）**：需求专属的接口 / 流程 / 设备 / 夹具测试 —— 批次内统一放需求测试目录，**包收口后随批归档并从工作区清掉**（§1）。

**门禁范围（按目录分两条规则）**：**随批测试目录**（整体被忽略）⇒ **豁免版本库跟踪过滤**；若沿用「只扫入库文件」，归档用例的 `@case` 载体**永远找不到** ⇒ 台账标对应执行器的条目**恒判 ❌**、快速验证在整个批次窗口内恒红，但**只扫「当前仍有台账」的包**，避免归档批次台账已删、测试还在时误报。**其余目录**（常驻测试）⇒ **只扫版本库跟踪的文件**（非版本库工作区回退全盘遍历）⇒ 本地留着的随批测试**不会**把门禁拖红；入库测试仍必须与台账配对（台账目录只保留常驻台账）。**同生同灭**：批次内 `rules/<ID>.yaml` 与该批测试一起存在、一起随批归档 ⇒ 收口后两者同时消失，门禁自然回到常驻层。

**回归网的边界（如实声明）**：代码级回归**只覆盖常驻层**。历史包的 PRD / 台账 / 测试随批归档，**不在日常回归网内** ⇒ 老功能的回归只能靠**发布前整体回归**（§3.4 照单逐功能点）。接受这个边界，是因为「每批测试都常驻」带来的历史耦合成本更高；若某条用例价值足够长期，**把它登记进常驻三类**即可。

### 6.8 角色输出契约（所有角色通用）

> **本节通用条款是唯一真源，各角色技能定义只引用不复述。**

1. **单一真源 + rev**：结论只住在一个**唯一台账**里（字段：`id / 结论 / 证据指针 / rev / 状态: terminal｜open`）；台账有唯一写入者，其余角色只读；交付必须写明**依据的 rev**。主控与角色**在消息里只传指针与触发**，**不传事实**。
2. **口径冻结 + errata**：进入 uat / test 观测即冻结口径；更正**只能追加** errata（原文删除线 + 触发者 + 依据 + 影响面），**禁改历史**。
3. **结论三档**：`实测 / 推断 / 未证`，写在报告首行；**禁跨档升格** ——「未复现」≠「已修」，「推断」≠「实测」（含主控）。
4. **数字必带出处**：数字的 `evidence` = 命令 + 时间 + 原始输出；**禁裸数字**；带限行的聚合**不得**报「共 N」。
5. **修复类交付必附两栏**：`同类点扫描清单`（搜索命令 + 命中位置 + 逐条处置及理由）+ `反例测试`（能复现原现象的用例）。缺任一栏 = **不算修完**。涉及状态 / 归属等关键列时，另附**写入方全量清单**，并随 diff 一起冻结。
6. **收口判据（二选一，禁用「未复现」单独结项）**：(a) 独占环境**连续 5 次全绿 + 根因已解释**，窗口**跨 ≥2 个时间边界、跨度 ≥60 分钟**；(b) 明确标注**「未解释」**并进「已知未知」清单，**随结论同行**。
7. **交付必附「执行台账」七行**（不润色、只事实）：跑过的命令 / 关键原始读数 / 落盘产物 / **收到的更正（谁 + 时间 + rev）** / 上抛问题（并说明为何不能自定）/ 等待空转 / 未追项。
8. **只读白名单默认授权，边界外不停手**：只读查询、设备读屏、日志 / 进程 / 端口只读、测试装置与夹具修复（不改实现语义）、口径措辞与产物位置、证据计数以一手记录为准、「是否需要独占环境」从宽认定。**必须送人仅六类**：动 schema / 权限 / 金额；**对外契约变更**；**不可逆操作**（删数据、生产迁移）；业务语义与观感的最终裁定；发版与提交；跨包批次范围。

> **产物上限**：单包 `reports/` 触线即合并为「**一页结论表 + 一份累积报告**」，历史进归档（§6.5 红线已有，本节强调**执行**）。

## 7. journal 纪律

**journal = 审计日志，每包一份，`docs/process/prd/<ID>.journal.jsonl`。**

```jsonc
{"at":"<ISO8601>","step":"pm","actor":"subagent:pm","action":"write","files":["docs/process/prd/<ID>.md"]}
{"at":"<ISO8601>","step":"test","actor":"subagent:test","action":"run","cmd":"<命令>","result":"red: 3 failed"}
```

1. **append-only** —— 只追加，**禁止覆写整文件**；也不得删改历史行。
2. **机器时间** —— `at` 必须取**机器时间**（由工具自动填），**禁用**模型自述时间；每行须带 `phase`，使阶段耗时 / 返工次数 / 阻断时长**可复算**。
3. **必须走工具** —— 一律通过**journal 追加工具**（框架自带脚本 / 插件工具 `process_journal`）写入；**禁止手工读-改-写**。
4. **并发防覆盖** —— 追加需**锁 + 指纹校验 + 原子替换**；并发只允许单行追加，每行必须自带 `actor`。
5. **守卫报警即停** —— 工具自校验失败（指纹不符 / 文件被外部改动）时**停下上报**，不得绕过。
6. **缺 journal 视为未交付** —— 每次 subagent 写入产物必须同步追加 journal；**主控 journal 只记三类**（裁定 / 派单 / 收口）。
7. **元数据滞后容许** —— 工具维护的元数据落后于文件是容许的；**不得手工改元数据**。

## 8. 流程分级

不是每个改动都值得三 Gate 三产物。触发条件写死：

| 路径 | 触发条件 | 走法 |
| --- | --- | --- |
| **全流程** | 动 schema / 动 RBAC / 动金额·分摊计算 / 新增对外接口 | **intake → Gate0（需求核对）→ draft → pm 出 PRD + 契约 + 设计与说明 → Gate1** → frozen → test 红 → Gate2 → dev → uat → Gate4 |
| **快速路径** | bugfix / UI 微调 | dev + 存量回归，**不建 PRD、不走 Gate0 / Gate1** |

> **需求核对与设计与说明是全流程包的强制环节**：人给的原料不得直接进 PRD；PRD 不得未经设计对齐就进 Gate1。二者缺一即视为未走流程。

### 8.1 验证强度分级

| 改动性质 | 验证强度 | 说明 |
| --- | --- | --- |
| 注释 / 常量 / 文案 | 静态检查 + 定向单测 | 不触发真机 |
| 源码逻辑（已有单测覆盖） | 单测 + 定向回归 | 不触发真机 |
| 源码行为（单测覆盖不到：平台差异、原生路径、真机 API） | **必须真机** | 桌面与真机行为不一致的面 |
| schema / RBAC / 金额·分摊 / 对外接口 | **全流程** | **不可降级** |

- **判定权**：改动性质归 orchestrator 判定；**是否降级验收强度归人决定，且降级必须在 Gate 摘要里显式写出，禁止静默降级**。
- **快速路径不得偷渡全流程事项**：快速路径改动若实际触及 schema / RBAC / 金额 / 对外接口，必须**退回全流程**。

## 9. 启动与收口协议（断线 / 重开必读）

1. **每次唤醒先取状态快照** —— 调插件工具 `process_status`（扫描 `input/prd/bugs` frontmatter，返回各包 status / gate0 / gate1 / gate2 / gate4 / prdVersion、journal 尾部、open bugs、状态位不一致警告、下一步动作）。**从状态续跑，不依赖聊天历史**。
2. **状态位不一致的处置**：快照报出不一致（如 `frozen` 配 `gate1: pending`）时**如实报人**，不得自行改状态位掩盖；由人裁定后按 §3.1 一起改两处。
3. **调 subagent 只传文件路径 + rev，不传聊天记录**（§6.8 第 1 条）；**每步动作完先写状态文件（含 journal），再进下一步**。
4. **唤醒前检查工作区是否干净**；不干净 → 停止并报告（避免误判角色越界改了测试，本工作区纪律见 `PROJECT.md` §6）。**发现 dev 改了测试 / e2e → 立即停止并报告。**
5. **Gate 前必须暂停**，输出两段式摘要（§4.1），等 approve；**不得自行 approve**。
6. **包收口归档**：包达到 `done` 后，按 §1 把需求专属产物与过程产物**打包进 `reports/_archives/`**（归档包 + 清单 + 校验和），再从工作区清掉需求专属件；`reports/_archives/**` 是**恢复源，不得删**。
7. **状态位落定**：Gate4 签收 ⇒ 落 `gate4: approved` → `status: done`；**两个字段必须一起写**。若项目配置通知（`PROJECT.md` §7），签收同时发一次通知（§4.2）。
8. **提醒提交但不自动提交**：每个包 `done` 后提醒人提交（提交信息带包 ID）；失败可单独回滚。**禁止自动提交**。提交范围以「包」为单位切分，禁止夹带别的包的在途改动 —— 提交前逐文件核对身份，不属本包的留在工作区，并在回报里显式列出「有意排除」清单。
9. **依赖的测试 / 脚本 / 配置随包一起提交**：只提交未跟踪文件 = 破状态（新页面无路由、新脚本无引用、新测试缺 setup 支撑）。**共享文件改动必须文档与真命令同时改**：只改文档等于没改（真命令才是门禁执行的东西）。

## 10. 过程载体与脚本约定

> 过程脚本 / 验收载体：**放哪、怎样才合规**。**编写细则与登记区在载体侧 README**（`docs/process/tools/README.md`，不进版本库）；本节只写规则。

### 10.1 放哪

- **唯一家 = `docs/process/tools/<包>/...`**（该目录由忽略规则排除）。
- **什么算过程载体**：验收载体 · 探针 · 夹具播种 / 清理 · 截图 / 取证 · 一次性数据核对 —— 为**某一批**产出的过程件。
- **为什么不进版本库**：一次性过程产物、不是产品代码；进版本库只会**淹没代码审核面**。
- **长期复跑的不放这**：需长期复跑 ⇒ 提升为**正式测试**（测试目录，随版本库版本化）。
- **长期复跑的「流程闸门」⇒ 生产脚本目录（受版本控制）**：放载体目录的脚本不入版本库 ⇒ **换台机器即失效**（命令槽会指向不存在的文件）。
- **维护归属**：载体由 **test** 维护；面向真机 / Web 驱动的操作脚本属主 **uat**。
- ⚠ **代价（已知并接受）**：别人检出后**不能直接复跑验收**，需从本目录或批次归档区取回。

### 10.2 合规要求

1. **在仓库根执行**；类型与用法以脚本头部注释为准；**仓库根必须动态查找，禁硬编码相对层级** —— 算错一层不是报错，而是**证据静默写进错目录**。
2. **转译模式约束**（如按 CJS 转译）⇒ 禁用该模式下不支持的语法与顶层动态导入。
3. **必须断言证据落点**（越界即非零退出；落点覆盖变量同样受断言约束）；**回归靠运行证据、不靠版本控制状态**：动过载体，报告附**复跑读数（含反向对照）**。

### 10.3 留在版本库内的（**不是**过程载体，勿移）

**门禁与流程命令常驻生产脚本目录**（journal 追加 · 台账门禁 · 落点门禁 · 版本同步），**勿当过程件搬走**。**批次生产迁移 / 运维脚本**：**未提交期间**须在载体侧登记区添加一行（登记即放行），**提交后立即删行**；⚠ 登记区在**不进版本库**的载体目录里 ⇒ **已提交的文件无需登记**，门禁只判「会进下一次提交」的未跟踪文件。**归档区是恢复源，不得删除**（§1 · §9 第 8 条）。

## 11. 附则：读源、分诊与环境纪律

### 11.1 读源边界按角色分层

- **pm** 允许读**数据层 schema** 与**接口路由签名**（路径、方法、入参 / 出参名、表名与字段名）；仍禁止读服务实现逻辑、测试、e2e、日志。
  - **契约与现状对齐时，证据来源只认**：① 人的裁定与 `input/**` 里的人给原文；② 规则台账 / 裁定登记 / journal；③ 接口路由与数据层 schema 的**签名**；④ **由 test 执行取得的行为级证据**（HTTP 层观测、复跑输出）。
  - **不得以「我读了实现」作为契约表述的依据** —— 契约若照抄实现，就永远照不出实现错误。**确需突破时必须当成一次越界登记**：写进契约与报告、说明读了什么与为什么、并报 orchestrator —— 承认越界不等于把越界变成惯例。
- **test** 白名单与 pm 一致，另可读既有测试与测试辅助；禁读业务实现细节。
- **uat** 是**唯一全禁角色**：禁读源码、测试、e2e、日志与任何代码 / 测试产物。

### 11.2 契约以现状为基线；PRD 是分区，不是删减

每个端点标 `alignment` —— `keep`（沿用现状）/ `change`（现状 → 目标，必附差异）/ `new`（新增）；复用字段须与数据层 schema 命名一致。**读现状 ≠ 接受现状**：现状与目标冲突时写进 `change` 并给理由，禁止静默抄现状。

存量（已实现）AC 保留并按其口径写断言 —— 这些断言若变红，即「现状与新口径不符」的真缺口，是本期最值钱的产出；新增区只放未实现的新实体 / 新端点 / 新行为。

### 11.3 红灯归因与契约漂移分诊

**红灯三类归因**（禁止混报「全红」）：**`401` = 基建假红**（测试装置未过认证）⇒ 自查修掉、重跑，**不计缺口**；**`200`（断言应为 `403`）= 真缺口**（如存量端点无权限码校验）⇒ 记账进真缺口清单，dev 阶段修；**`404` = 契约漂移**（端点不存在）⇒ 停止写测试，BLOCKED 上报打回 pm，**不进 dev**。

**契约漂移分诊判据**（禁止当二选一处置）：① 需求真要的（AC 有依据）→ 契约改标 `change`，dev 实现；② 纯形态命名（前端已消费现状）→ 契约对齐现状标 `keep`，统一化挂技术债，不改已验证实现；③ 测试装置未复刻环境 → 修基建，两边都不动。

### 11.4 测试环境纪律

① 自组装应用必须复刻真实入口的全局行为（错误处理、日期与大数据类型序列化等），否则产生「格式」类假红；② **禁改共享用户数据**（真实测试账号）；需真实用户 → 播种专用测试账号（含无权限角色以覆盖 `403` 面）；③ 库写副作用先报告后执行，已发生的记 journal + 报备恢复方案；④ **基线快照**（开工前的测试结果）必须在 dev 开工前落盘，作为**前后对照留痕**（**不是判据** —— 判据是「本次验证无红」；对照只为排查时看清「哪几条是新出的」）；⑤ 共享账号 / 环境状态被改动须在 Gate 摘要置顶。

### 11.5 subagent 版本控制与环境纪律

① subagent **禁用一切改变工作区的版本控制命令**（切换状态、还原、清理、提交），只允许只读；② 基线对照 = 读快照文件比对测试结果，不是切换版本状态；③ dev 每次交付时 orchestrator 把完整 diff 存 `reports/dev-patches/<ID>-<n>.patch`（防丢失，可秒恢复）；④ orchestrator 验收 dev 时先核「声称改动的文件清单 vs 实际 diff 统计」一致性；⑤ 恢复被破坏的改动属 orchestrator 职责（恢复 ≠ 新实现，不违 TDD 边界）。

**构建 / 打包类任务的「存底 → 还原」必须限定作用域（硬约束）**：只允许存底、还原「该次构建 / 打包**实际会改写**的文件」，**禁止**用「当前所有脏文件 / 全部受跟踪文件」当存底清单；**实证确定作用域** —— 先跑一次构建，比对前后差异，把**真实被改写的文件**列成清单，清单之外的**一律不碰**；与 ① 同源，都是「**不得用工作区级操作解决文件级问题**」。

### 11.6 人类所见即所得（通知纪律）

凡项目配置了通知渠道（`PROJECT.md` §7），通知**只写两段**（完成了什么 / 还需要裁定什么），一句一件、只讲结论，**细节一律不进通知**；需要人拍的项只在 Gate 摘要里问，**通知不复述**；**不许静默** —— 发送失败一律如实上报，不得静默跳过，也不得改发别的渠道凑数；凭据只从环境变量取，**不得在脚本或文档里写死**。

## 12. 速查：一次全流程包的最短路径

```text
人给原料 → 主控 process_status 取状态 → 起草 input/<ID>-需求核对件.md
  └─【停】Gate0 ──approved──▶ pm：PRD + 契约 + 设计与说明（逐条对齐 R-NN）
       ├─ 触及 UI 的包 ──▶ ui-designer：UI 规格（组件判定 / 状态矩阵 / 文案定稿）+ **原型图与视觉数值**（`prototypes/<ID>/**`，跑几何门禁），随 Gate1 一并审
       └─【停】Gate1 ──approved──▶ status=frozen ──▶ test：写测试（红）+ 缺口盘点 + 归因
            └─【停】Gate2 ──approved──▶ status=red ──▶ dev：实现到绿 → status=implementing
                 └─ test：独立复跑（冻结 diff + 基线声明）→ status=uat
                      └─ uat：黑盒两段观察 → pm：验收完备性审核
                           └─【停】Gate4 ──approved──▶ status=done
                                └─ 通知（可选）→ 包收口归档 → 提醒人提交
多包 done ──▶ release 回归（test + uat + 三评审）──▶ 上线
```

**一句话记住**：**状态写文件、判据写断言、证据在三层、Gate 只四停、裁判不兼运动员、红不许变绿。**
